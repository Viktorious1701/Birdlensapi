# Story 5.5: PayOS Webhook Handler (Subscription Activation)

## Status
Done

## Story
**As the** System,
**I want** a public webhook endpoint to securely receive and process payment status updates from PayOS,
**so that** I can automatically activate user subscriptions and notify them of their upgrade.

## Acceptance Criteria
1. A `POST /api/v1/webhooks/payos` endpoint is created that is publicly accessible (excluded from JWT filter).
2. The handler verifies the integrity of the incoming request by recalculating the HMAC-SHA256 signature of the payload using the configured `app.payos.checksum-key`.
3. If the signature is valid and the status is `PAID`:
    - Retrieve the `orderCode` from the payload.
    - Fetch the `PendingPaymentContext` from Redis using the `orderCode`.
    - Retrieve the `User` from the database and the `Subscription` details.
    - Update the user's `subscription_id` and calculate the `subscription_expires_at` (current time + subscription duration days).
4. The service publishes a `SubscriptionActivatedEvent` to the `notifications.exchange` (routing key: `notification.subscription.activated`).
5. The webhook returns a `200 OK` response to PayOS regardless of internal business logic outcomes to prevent retry storms (unless the signature is invalid).
6. An integration test simulates a valid "PAID" webhook call and verifies:
    - The user's record in PostgreSQL is updated.
    - The Redis key is deleted (cleanup).
    - A message is published to RabbitMQ.

## Dev Notes
- **RabbitMQ Topic Exchange**: Added `TopicExchange` to `RabbitMQConfig` mapped to `notifications.exchange` preparing the infrastructure for Epic 6 routing bindings.
- **Fail-Safe Processing**: A `try/catch` was deployed globally inside `PayOSService.processWebhook`. Any database failure, Redis timeout, or missing context simply prints to the error log allowing the process to still return an HTTP `200 OK`. Returning 4xx or 5xx codes causes automated webhook vendors to infinitely hammer endpoints thinking they dropped packets. We only return `400` during an active spoofing (Invalid Signature) attempt.

### Testing
- Fully integrated test utilizes `java.security.Mac` to perfectly simulate PayOS signature bindings, overriding network configurations and pushing real JSON shapes across HTTP via `WebTestClient`. Proves Redis caching is successfully wiped immediately following a verified upgrade.
