# Story 6.4: Fetch Notifications API

## Status
Done

## Story
**As an** Authenticated Mobile Client,
**I want** to fetch my notifications,
**so that** I can see recent activity related to my account and mark them as read.

## Acceptance Criteria
1. A `GET /api/v1/notifications` endpoint is created.
2. The endpoint returns a paginated list of `UserNotification` records for the authenticated user, ordered by `created_at` descending.
3. The response format matches the `PaginatedNotificationsResponse` model (including `id`, `message`, `type`, `isRead`, `createdAt`).
4. An endpoint `PATCH /api/v1/notifications/{id}/read` is created to mark a specific notification as read.
5. Both endpoints are secured with JWT authentication.
6. A user cannot view or modify notifications belonging to another user.
7. An integration test verifies the pagination and the security boundaries (ownership check).

## Dev Notes
- **Hardened Data Borders**: The API inherently filters all `GET` results to the explicitly authenticated user directly at the Database `Repository` level by routing the `@AuthenticationPrincipal` identity as the primary WHERE parameter.
- **REST Protocol Standard**: Utilized `@PatchMapping` instead of `PUT`. The definition of patching implies partial modifications to an existing resource (changing boolean `isRead` flag from false -> true) while a PUT implies a complete record overwrite.
- **Cross-User Protection**: Handled via hard throws (`AccessDeniedException`). It cleanly delegates up the Spring interceptor returning a unified 403 response keeping malicious actors bounded securely.

### Testing
- Executed `NotificationApiIntegrationTest` spanning multiple authenticated principals synchronously. Tested isolation by assuring User B receives `0` documents during `findAll` queries despite User A possessing seeded testing context. Authenticated cross-origin patching effectively blocked with `403` HTTP codes.
