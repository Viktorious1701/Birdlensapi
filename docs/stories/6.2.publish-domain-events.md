# Story 6.2: Publish Social and Payment Events to RabbitMQ

## Status
Draft

## Story
**As a** Backend Developer,
**I want** to refactor the Post and Payment services to publish specific domain events,
**so that** the notification system can process them in the background without slowing down user actions.

## Acceptance Criteria
1. When a user likes a post, the `toggleLike` logic publishes a `PostLikedEvent` to the `notifications.exchange` with the routing key `notification.post.liked`.
2. When a user comments on a post, the `addComment` logic publishes a `NewCommentEvent` to the `notifications.exchange` with the routing key `notification.post.commented`.
3. The `SubscriptionActivatedEvent` (from Story 5.5) is verified to be publishing to the `notifications.exchange` with the routing key `notification.subscription.activated`.
4. Event payloads include the necessary IDs for the worker to create a notification (e.g., `receiverId`, `actorId`, `postId`, `messageSnippet`).
5. Integration tests verify that these specific messages arrive at the exchange when the API endpoints are called.

## Tasks / Subtasks
- [ ] Task 1: Create/Update Event DTOs (AC: 4)
  - [ ] Create `PostLikedEvent` (postId, likerUserId, postOwnerUserId).
  - [ ] Create `NewCommentEvent` (postId, commenterUserId, postOwnerUserId, commentSnippet).
- [ ] Task 2: Refactor PostService (AC: 1, 2)
  - [ ] Inject `RabbitTemplate` into `PostService`.
  - [ ] Update `toggleLike`: Only publish the event if a new Like was created (do not publish on "Unlike").
  - [ ] Update `addComment`: Publish the event after the comment is successfully saved.
- [ ] Task 3: Verify PayOSService (AC: 3)
  - [ ] Ensure the `SubscriptionActivatedEvent` fired in Story 5.5 matches the routing key `notification.subscription.activated`.
- [ ] Task 4: Integration Testing (AC: 5)
  - [ ] Update `SocialInteractionIntegrationTest` to verify messages are published to RabbitMQ using a test queue/listener.
  - [ ] Update `WebhookIntegrationTest` to verify the payment event routing.

## Dev Notes
- **Routing Strategy**: We are using a `TopicExchange`. This allows us to use routing keys like `notification.post.*` or `notification.#`.
- **Performance**: Do not block the user's response if RabbitMQ is down. However, since we are using `@Transactional`, if the DB save fails, the event should not be sent.
- **DTOs**: Ensure these event classes are `records` for immutability and are located in `com.example.birdlensapi.messaging.events`.

### Testing
- You can use `RabbitAdmin` in your test code to check the message count in the queues or use a `@RabbitListener` in the test class to "spy" on the exchange.
